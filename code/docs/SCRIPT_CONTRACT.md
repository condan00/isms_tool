# 항목 스크립트 계약 (AI에게 항목 스크립트를 시킬 때 프롬프트 맨 앞에 붙이세요)

엔진(Python)이 `scripts/items/<항목코드>.sh` 를 `bash <파일> check|apply|list` 로 실행한다. 파일 이름은 항목 코드와 정확히 같아야 한다(예: `U-16.sh`).

## 출력
- stdout **마지막 줄** = `STATE|근거` 한 줄. STATE 는 `GOOD` `VULN` `MANUAL` `NA` `ERROR` 중 하나.
- 마지막 줄 앞의 줄은 상세 목록(대상 파일 경로 등)으로 취급한다. 그 밖의 안내 문구는 stdout 에 쓰지 말고 stderr 에 쓴다.
- 비밀번호, community 문자열 같은 값은 근거에 넣지 않는다.
- 종료코드: 정상 0, 오류 1 이상. `check` 에서 VULN 이어도 종료코드는 0.

## 항목마다 만들 것 (엑셀 '쉘스크립트 가능' 열 기준)
- O, ? : `check` + `apply` + `list` 스크립트, 그리고 `data/guides.json` 의 가이드 블록. (? 는 TUI 에서 확인 후 적용)
- X : `check` + `list` 스크립트와 가이드 블록. `apply` 는 만들지 않는다(실행하면 usage 오류 종료코드 2).
- 전체 파일 검색 항목(U-15, 23, 25, 26)도 엑셀 `?` 이므로 `check`+`apply`+`list`. `heavy` 라 기본 선택에서만 빠지고 확인 후 적용한다. 대상이 300건을 넘으면 자동 조치하지 않고 MANUAL.
  U-15: 소유자/그룹을 root 로 변경(삭제 안 함) · U-23: 패키지 소유가 아니거나 홈/임시 경로의 SUID/SGID 비트만 제거 · U-25: other 쓰기 비트 제거 · U-26: /dev 안의 일반 파일 삭제(50MB 이하, 스냅샷으로 내용 복구)

## 패키지 확인 (엑셀 '패키지 확인 필요' = O)
기본 설치가 아닌 서비스·패키지를 다루는 항목은 `check`/`apply`/`list` 맨 앞에서 설치 여부를 먼저 확인한다.
- 대상 패키지(또는 서비스 유닛)가 하나도 없으면 점검하지 않고 `NA|대상 패키지(...)가 설치되어 있지 않아 점검 대상이 아닙니다` 로 끝낸다(조치도 하지 않음).
- 확인은 `rpm -q`(Rocky) / `dpkg -s`(Ubuntu) 로 하고, 둘 다 없으면 판별 불가로 보고 그대로 점검한다. 서비스는 `systemctl list-unit-files` 로 유닛 존재도 본다.
- 설치되어 있지 않다는 이유로 패키지를 설치하지 않는다(설치는 도구가 하지 않는다).

## 동작
- `list`: **읽기 전용**. 줄마다 `/절대경로<TAB>설명` 을 출력하고 마지막 줄은 `GOOD|N개 파일`(대상이 없으면 `NA|사유`).
  엔진은 (1) 조치 직전 스냅샷 대상(`touches.files` 에 더해 이 목록)과 (2) 가이드 파일의 '관련 파일 목록' 으로 쓴다.
  `apply` 가 바꾸는 파일은 반드시 `list` 에 나와야 복구된다. 경로는 절대 경로이고 `..` 가 없어야 한다(아니면 무시).
- `check`: **읽기 전용**. 시스템을 절대 변경하지 않는다. 서비스가 없으면 `NA`, 사람이 판단해야 하면 `MANUAL`.
- `apply`: 취약 항목만 최소한으로 변경한다. 스냅샷(백업)은 엔진이 만든다. 스크립트는 백업/복구 코드를 넣지 않는다.
  끝에서 스스로 재확인해 기준을 충족하면 `GOOD|조치 내용`, 아니면 `ERROR|사유` + 종료코드 1 (엔진이 자동 원복한다).
- 권한 판정은 숫자 `==` 비교가 아니라 "허용 범위를 넘는 비트" 로 한다. 이미 더 엄격하면 양호.
- **스크립트 안에서 `sudo` 를 쓰지 않는다.** 프로그램 전체가 이미 root 로 실행되며 스크립트는 그 권한을 물려받는다.
- 삭제(`rm`, `userdel`), `chmod -R`, 패키지 설치/삭제, 전체 파일 변경은 금지. 이런 항목은 `guide` 유형으로 두고 목록·권고만 출력한다.
- `set -e` 에 의존하지 않고, 모든 변수는 따옴표로 감싼다. 환경은 `PATH`, `LC_ALL=C`, `ISMS_ITEM_ID`, `ISMS_OS_KEY`, `ISMS_PKG_MANAGER` 만 전달된다.
- 시간 제한: 일반 항목 120초, `heavy` 항목 900초.

## 항목 정의(data/items.json)와의 관계
- `touches.files` 에 적은 파일은 엔진이 `apply` 직전에 스냅샷으로 저장한다. 스크립트가 바꾸는 파일은 **전부** 여기에 적어야 복구된다.
- `type`: `auto`(바로 적용) / `approve`(TUI 에서 확인 후 적용) / `guide`(직접 적용하지 않고 점검+가이드).
- `fix_supported_os` 에 없는 OS 에서는 점검만 가능하다. 실제 VM 에서 검증한 OS 만 적는다.

참고 구현: `scripts/items/U-16.sh`

## 패키지 미설치 처리 (pkg_gate)
- 패키지 설치됨 → 정상 점검·조치. 메일처럼 패키지가 여러 종류면 **설치된 패키지에 대해서만** 점검·조치한다.
- 패키지 미설치 + 관련 설정 파일/디렉터리(주석·빈 파일 제외)가 남아 있음 → `MANUAL` (점검 필요, 자동 조치 안 함).
- 패키지 미설치 + 관련 파일도 없음 → `NA` (조치 건너뜀, 가이드 파일도 만들지 않음).
- 적용 스크립트: U-20,21,27,35,45,46,47,48,50,51,55,57,59,60,61 (공통 함수는 tools/config_lib.sh).

## 파일 소유자/권한 변경 (safe_fix)
- 사용자 홈 등 일반 사용자가 바꿀 수 있는 경로에는 `chown`/`chmod` 를 직접 쓰지 않고 `safe_fix 경로 [소유자] [chmod식]` 를 쓴다.
- 파일을 먼저 열어 fd 로 소유자/권한을 바꾸고, 심볼릭 링크이거나 점검 때와 다른 파일이면 건드리지 않는다(링크 바꿔치기 방어).
- U-01 조치는 root 대신 접속할 관리자(wheel/sudo, 암호 또는 SSH 키)가 없으면 변경하지 않는다.

## 서비스 재적용 정책
- 끊김이 없는 reload: sshd(U-01), named(U-51), postfix(U-48), samba·NFS(`exportfs -ra`, U-35), xinetd/inetd(설정을 바꾼 경우).
- FTP(vsftpd/proftpd, U-35·U-57)는 설정 검사 후 자동 재시작한다. 재시작 실패 시 ERROR → 엔진이 파일과 서비스 상태를 원복한다.
- sendmail(U-46·U-48)은 자동 재시작하지 않는다. 결과 문구에 `[수동 재시작 필요: ...]` 를 넣고 TUI/CLI 가 경고로 보여 준다.
- 재시작/reload 하는 서비스는 `list` 에 `@service` 줄로 알려 스냅샷이 상태를 복구하게 한다.

## 엑셀 재검토로 `?`(승인 후 적용)가 된 항목 (U-05, 08, 10, 14, 22, 36, 67 + 전체 검색 15, 23, 25, 26)
- U-05: root 외 UID 0 계정의 UID 를 최대값+1 로 변경 · U-08: 관리자 그룹마다 root 외 1명만 남김(ISMS_INVOKER 우선) · U-10: 중복 UID 규칙(0=root 유지, 3000 미만=기본 계정 유지, 3000 이상=위 계정 유지, 새 UID=최대값+1 부터 순차)
- U-14: PATH 줄에서 '.' 과 빈 항목 제거 · U-22: root 소유 + 644 이하 · U-36: r 계열 서비스 비활성화 · U-67: 로그 소유자 root, 644 이하
- UID 변경(U-05, 10)은 usermod 가 UID 0 계정을 거부하므로 /etc/passwd 3번째 칸을 직접 바꾸고 홈·메일함의 예전 UID 소유 항목만 chown 한다. 실패하면 이미 바꾼 것을 되돌린 뒤 ERROR.
- 엔진은 스크립트에 `ISMS_INVOKER`(sudo 를 실행한 계정 이름)를 환경변수로 넘긴다.
